Sharing, rethought

Today one listener carries the address, the secret and the profile allowlist all at once. This note splits it into three layers (share, profiles, sessions), puts them on interchangeable transports (local, LAN, Tailscale, WebRTC), and specifies one short, scanner-friendly link format for all of them.

2. The model: three layers

Separate where it listens from who may get in, and give each recipient their own object.

Layer 1: Share

  • A share holds a secret (rech1_…), a host-side label/slug (never in the URL), its profiles, optional expiresAt, and a revoked flag.
  • Many shares can use one listener and one port. serve looks up the share from the presented key.
  • Revoking or rotating affects only that share.

Layer 2: Profile binding

  • rech share allow|deny <slug> <profiles…> changes the allowlist. The link stays the same, and connected clients see the change on their next call.
  • On the client, rech profile lists only that share's profiles (display names and emails, never folder paths), via a new GET /profiles.
  • A share created with "every profile" is a snapshot, so a profile registered later is never exposed without you knowing.

Layer 3: Sessions (reuses playwright-cli -s=)

  • The share id is added to the session hash, so two recipients can never reach each other's browser state.
  • Scoped session-list (only this share's sessions), close and delete-data are allowed. close-all and kill-all stay blocked.
  • Tab group = <share label> · <client label>, so the host can see in Chrome who is driving which tabs.

3. Transports

The share, the profile scoping (authorizeProfileRequest, resolveAllowedProfile) and the session hashing are the same for every transport. WebRTC is just another way to deliver the same requests.

4. Link format

A link only has to carry two things: where to rendezvous and one secret. Everything else is derived from the secret or kept on the host.

https://rechrome.pages.dev/#rech1_7fQxC9tZp2mVb8wLrN4hdK3kT9aQ

That's about 62 characters, compared with about 115 for …/room/#room=r…&s=e1.<64hex>. The secret is in the #fragment, which browsers never send to a server.

One fragment, any origin

LinkTransport
https://rechrome.pages.dev/#rech1_…WebRTC via the default signal host
https://sig.example.com/#rech1_…WebRTC via a self-hosted signal host
http://100.101.2.3:13775/#rech1_…Direct HTTP (LAN or Tailscale). Bearer = HKDF(S, rech/bearer).
http://127.0.0.1:13775/#rech1_…Local
rech1_… (bare)CLI only: the default signal host

rech connect finds the transport with one probe. A rech daemon answers /ping with its usual JSON; a signal host answers {"rech-signal":1}. There's no webrtc:// scheme, and every link opens in a browser to a landing page with a copy button. The page reads the fragment in browser JavaScript.

Deliberately not in the URL

  • Room id: derived as HKDF(S, rech/room).
  • Profile: the share decides. One profile means it's the default; several means rech --profile. Then a URL can never look as though it grants something it doesn't.
  • Slug/label: host-side only, shown in rech share ls, tab groups, and the client's rech status after connecting.

5. The rech1_ secret

rech1_  7fQxC9tZp2mVb8wLrN4hdK  3kT9aQ
└─┬──┘  └─────── 22 ───────┘  └─6──┘
  │     128 random bits,       CRC32 of the 16 secret bytes,
  │     base58, fixed width    base58, fixed width
  prefix + format version
ChoiceWhy
rech1_ prefixUnique, so secret scanners can match it with few false positives. sk- would collide with OpenAI-style keys and send leak reports to the wrong place. The 1 is the format version; the next format becomes rech2_.
128 bitsThe server only sees one-way HKDF outputs, and brute-forcing 2¹²⁸ offline isn't feasible. 256-bit hex would add about 40 characters for nothing.
base58Same length as base62 at 128 bits (22 characters), without the ambiguous 0 O I l, so a link read off a screenshot or a call survives. It also selects as one word on double-click (no - or _ in the body). Encode fixed-width by left-padding with 1.
CRC32 checksumScanners can reject look-alikes without contacting any server, and rech connect can say "link copied incompletely" instead of failing later.

Regex (gitleaks, TruffleHog, and rech's own log redaction):

\brech1_[1-9A-HJ-NP-Za-km-z]{28}\b

Leaks: make the link worthless, catch it early, keep it short-lived

We don't depend on GitHub or any scanner. There are three layers, and none needs anyone else's cooperation.

a. The link is a one-time invite (device pinning)

  • On first rech connect, the client redeems the invite over the encrypted channel, and the host mints a device credential: its own rech1_ secret, saved only on that device. (Built this way instead of a client keypair: same property, and every transport, room and key derivation then works the same for invites and devices.)
  • The invite is then used up, or allows at most --devices N. Later connections use the device's own secret, which gets its own WebRTC room and its own HTTP bearer.
  • A link pushed to GitHub, pasted in Slack or seen in a screenshot after it was used no longer works. If a stranger uses it first, the real recipient can't connect, an obvious signal to the host, who runs rech share revoke.
  • Optional --approve: each new device waits for the host, like Bluetooth pairing: new device "mbp-alice" wants in on share alice: approve? [y/N].
  • The device key also becomes the client identity in the session hash, so one device's sessions belong to that device.

b. Prevention

  • Env-file check (built now): wherever RECHROME_URL is saved or loaded from, rech checks whether the file is committed, staged or not git-ignored in git, and on Unix whether it's readable by other users. It only warns, and the command still runs. It shows in rech status (secret: ⚠ …), after rech connect, and after share --save. A previously committed but since untracked file isn't flagged, because it held an older key.
  • rech connect saves to .rechrome/.env.local, whose folder git-ignores itself, and writes files 0600.
  • Upstream gitleaks and secretlint rules (ordinary pull requests, no partner agreement), so pre-commit and CI catch rech1_ before a push.
  • Documented recipe for GitHub custom patterns: an org can add the regex to its own secret scanning, which alerts that org.

c. Short lifetimes

  • Unused invites expire after 24 h (--invite-ttl).
  • WebRTC shares expire after 30 days by default (--expires, rech share renew), since anyone on the internet who has the link can reach them. LAN and Tailscale shares default to no expiry.
  • rech share ls shows expiry, devices and last use, so stale shares are easy to spot.

Not planned: polling GitHub code search ourselves. The GitHub secret scanning partner program needs an application and an always-up endpoint; maybe later, and invites make it mostly unnecessary.

Other secrets could get their own prefixes so a report says exactly which one leaked: rechx1_ extension token, rechm1_ daemon management key. That's optional; only the share secret is meant to leave the machine.

6. WebRTC protocol

This follows agent-yes (lab/ui/cf/worker.ts, lab/ui/e2e.js, ts/share.ts, ts/webrtcRemote.ts), which has already shipped it. We reuse its crypto and relay design but not its link shape.

Key derivation (all from the one secret S)

room      = HKDF(S, "rech/room")    → signal room id (server sees it)
authToken = HKDF(S, "rech/auth")    → room admission (server sees it, one-way)
bearer    = HKDF(S, "rech/bearer")  → HTTP transports' Authorization header
th        = SHA-256(offer.sdp ‖ answer.sdp)   (includes both DTLS fingerprints)
k_h2c, k_c2h = HKDF(S, th, "rech/key/…")      → AES-256-GCM per direction

Because the keys depend on th, a signal server that swaps in its own fingerprints ends up with keys that don't match, and the key-confirmation step fails closed. A fully compromised signal server can only block connections and see metadata.

Frames (after decryption)

client → host : {t:"req", id, method, path, body?} | {t:"abort", id} | {t:"confirm", nonce, echo?}
host → client : {t:"res", id, status, ct} | {t:"data", id, seq, chunk} | {t:"end", id, seq, error?}

Chunks are 12 KB or less of plaintext, well under the DataChannel message limit. Screenshots under /files/ stream as several data frames.

Host side

rech serve keeps one hibernated signalling socket for each WebRTC-enabled share. A decrypted request is forwarded to that share's listener, so the share's profile allowlist applies exactly as it does over HTTP. Bun has no built-in RTCPeerConnection; agent-yes runs node-datachannel/polyfill under Bun in production.

Client side: a persistent bridge

Each rech command is a separate process, and a fresh handshake per command would cost about 1–3 s. So rech connect starts a small local bridge on 127.0.0.1 (inside the local rech serve if there is one). It holds the DataChannel, and RECHROME_URL points at it. All existing fetch-based commands then work unchanged, which is the same approach as agent-yes's webrtcRemote.ts.

7. Signal server on Cloudflare

rechrome.pages.dev is a static Pages project on the SNOLAB account, Git-connected and serving public/. agent-yes's signal Worker is on the same account.

OptionEffortNotes
A. Use s.agent-yes.comnoneFastest way to build against. rechrome would depend on agent-yes's domain, and its hello carries a different link format.
B. rechrome-signal Worker + Pages FunctionsmallCopy the Room Durable Object. functions/ on Pages binds it (script_name), since Pages can't define Durable Objects itself. Users only ever see rechrome.pages.dev. recommended
C. Move the site to a Worker with assetsmediumOne Worker for the site and the signal server, as agent-yes does. Also opens the way to a custom domain later.

Free-tier fit

  • SQLite-backed Durable Objects run on Workers Free: 100k requests/day. Incoming WebSocket messages count 20:1; outgoing messages and pings are free.
  • Idle hibernated objects aren't billed for duration. Answer the host keepalive with setWebSocketAutoResponse so pings never wake the object. agent-yes found that waking on every ping caused about 99.9% of its Durable Object time.
  • One handshake is a few dozen messages, so thousands of connects per day fit.
  • STUN: stun.cloudflare.com, free and unlimited.
TURN policy. Cloudflare TURN's first 1,000 GB/month is free, then $0.05/GB, billed to whoever owns the key. There's no shared central relay. As in agent-yes, the host owner can set CF_TURN_KEY_ID/CF_TURN_API_TOKEN and serve mints 1-hour credentials for each peer. Otherwise it's STUN only, and on a failed connection rech connect suggests Tailscale.

Prefer your own? Any server that speaks the signal protocol works: Cloudflare on your account, a Bun process on a VPS or home box, Docker, or the relay built into rech serve. See the self-hosting tutorial.

Signal server hardening: per-IP rate limits, a cap on peers per room, no message logging, and refusal of any non-hello first frame.

8. CLI surface

Host

rech share new work@ personal@ --name alice --via webrtc,tailscale \
  --expires 7d --devices 1 [--approve] [--invite-ttl 24h]
  → https://rechrome.pages.dev/#rech1_7fQxC9tZp2mVb8wLrN4hdK3kT9aQ
  → rech connect rech1_7fQxC9tZp2mVb8wLrN4hdK3kT9aQ
rech share ls                      # shares, transports, profiles, live sessions
rech share allow alice ci@         # live allowlist edits; link unchanged
rech share deny  alice personal@
rech share rotate alice            # new secret (new room); old link dies
rech share devices alice           # pinned devices, last use; --rm <device>
rech share approve alice           # with --approve: let a waiting device in
rech share renew alice --expires 30d
rech share revoke alice            # also closes alice's sessions
rech listener ls|add|set|rm        # transports only (address, port, publicUrl)

Client

rech connect '<url>' | rech1_…   # checksum, probe, pick transport, save RECHROME_URL
rech profile                       # profiles this share allows
rech --profile work open https://example.com
rech -s=login open https://accounts.example.com
rech session ls | close <name>     # only this share's sessions
rech status                        # share label, transport, bridge health

9. Migration: nothing breaks

  • Each scoped listener becomes a listener plus one implicit share with the same key and profiles, so existing ?profile=…#key=… links keep working.
  • listener allow/deny/rotate-key become aliases that act on that implicit share.
  • share --all becomes a share with every profile (a snapshot), with no new port.
  • A fragment containing key= takes the old code path; a rech1_ fragment takes the new one.
  • The session hash only gains the share id for new shares, so live sessions on old links aren't orphaned.

10. Open questions

  1. Several clients on one share: should they see each other's sessions? Proposal: no, separate by client identity; the host sees everything.
  2. Per-share command scope: unlock eval per share (--allow-eval)? It's easy to add but a real trust escalation, so it should be off by default and shown loudly in share ls.
  3. Sharing e2e.js with agent-yes: publish it as a package, or vendor it under lib/? One copy, two projects, no drift.
  4. Browser client: should the landing page also be able to drive a share directly (view tabs, take screenshots) over WebRTC, beyond being a copy-command page?
