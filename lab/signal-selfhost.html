Run your own signal server

WebRTC shares need a rendezvous where the host and client swap connection details before they talk directly. By default that's rechrome.pages.dev. This tutorial covers running your own: five ways, from a free Cloudflare Worker to a box under your desk.

Built in feat/sharing: the Bun relay is rech signal serve (signal-relay.ts), the Cloudflare version is signal/cloudflare/, and hosts pick a server with rech share new … --signal <url> or RECH_SIGNAL. The maintained copy of this tutorial is docs/signal-selfhost.md.

1. What you're trusting (less than you'd think)

A signal server only relays the handshake. It never sees the share secret: it gets a room id and an auth token, both one-way HKDF outputs of the secret. The encryption keys depend on the exchanged SDPs, so the server can't substitute its own. After the handshake, traffic goes peer to peer.

A hostile or compromised signal server canIt cannot
Refuse or drop connections (DoS)
See which IPs meet in which room and when
Count connections		Read or change browser traffic
Learn the share secret or derive keys
Join a share or impersonate a host

So self-hosting is about availability (not depending on our free tier), metadata (who connects to whom stays with you), and policy (a corporate network that only allows its own hosts), not about who can read your browser.

Whichever you choose, it needs HTTPS/WSS when clients are on other networks, and it must allow WebSocket upgrades.

3. A. Cloudflare Workers (your account)

This is the same design as the default server: one SQLite-backed Durable Object per room, using WebSocket hibernation so an idle host costs nothing. It fits the Workers Free plan (100k requests/day; incoming WebSocket messages count 20:1).

# 1. get the template (signal/cloudflare/: worker.ts + wrangler.jsonc)
git clone https://github.com/snomiao/rechrome && cd rechrome/signal/cloudflare

# 2. log in and deploy (wrangler needs Node.js, not Bun, for `wrangler dev`)
npx wrangler login
npx wrangler deploy
# → https://rech-signal.<your-subdomain>.workers.dev

For a custom domain whose zone is on the same account, uncomment the route in wrangler.jsonc:

"routes": [{ "pattern": "signal.example.com", "custom_domain": true }]

4. B. Bun on a server + Caddy

The relay is one file with no dependencies beyond Bun. Rooms live in memory and disappear when everyone leaves.

# on the server
curl -fsSL https://bun.sh/install | bash
bunx rechrome signal serve --host 127.0.0.1 --port 8787

Put TLS in front. Caddy gets certificates automatically:

# /etc/caddy/Caddyfile
signal.example.com {
  reverse_proxy 127.0.0.1:8787
}

Keep it running with systemd:

# /etc/systemd/system/rech-signal.service
[Unit]
Description=rech signal relay
After=network-online.target

[Service]
ExecStart=/home/rech/.bun/bin/bunx rechrome signal serve --host 127.0.0.1 --port 8787
User=rech
Restart=always
NoNewPrivileges=true
ProtectSystem=strict
ProtectHome=read-only

[Install]
WantedBy=multi-user.target
sudo systemctl enable --now rech-signal caddy

5. C. Home box + Tailscale Funnel

Funnel gives a machine on your tailnet a public https://<machine>.<tailnet>.ts.net URL, without opening a port or buying a domain. It suits a Mac mini or NAS that stays on.

bunx rechrome signal serve --port 8787
tailscale funnel --bg 8787
# → https://mini.tail1234.ts.net/  (public; Funnel must be allowed in your tailnet policy)

Why Funnel and not Serve: tailscale serve is tailnet-only. If every client is on your tailnet, skip WebRTC and use a tailscale transport share directly. Funnel is for clients outside the tailnet. On macOS, run the relay as a LaunchAgent so it survives logout (see docs/macos-daemon.md for the pattern).

6. D. Docker

# Dockerfile
FROM oven/bun:1-alpine
RUN bun add -g rechrome
USER bun
EXPOSE 8787
CMD ["bunx", "rechrome", "signal", "serve", "--host", "0.0.0.0", "--port", "8787"]
docker build -t rech-signal .
docker run -d --restart=always -p 127.0.0.1:8787:8787 rech-signal

Then put TLS in front (Caddy as in B, or your platform's HTTPS). On Fly.io, Render or Railway the platform handles TLS, so expose 8787 and use the HTTPS URL they give you. Run one instance: rooms live in memory, so a host and its client must reach the same process. Use sticky sessions or a single replica.

7. E. Quick tunnel (testing only)

bunx rechrome signal serve --port 8787 &
cloudflared tunnel --url http://127.0.0.1:8787
# → https://random-words.trycloudflare.com

There's no account and no uptime guarantee, and the hostname changes every run, which invalidates every link made with it. Use it for trying things out, not real shares.

8. Point rech at it

Only the host chooses the signal server. Its origin becomes the link, so clients need no setup.

# one share
rech share new work@ --signal https://signal.example.com/
  → https://signal.example.com/#rech1_7fQxC9tZp2mVb8wLrN4hdK3kT9aQ

# default for every new share on this machine
export RECH_SIGNAL=https://signal.example.com/

# the client side does nothing special:
rech connect 'https://signal.example.com/#rech1_…'   # probes /ping → {"rech-signal":1} → WebRTC

Changing a share's signal server changes its link, like rotate. Existing devices pinned to the share keep working once they learn the new origin from the host over their open channel.

9. Verify

curl https://signal.example.com/ping
# {"rech-signal":1}

A full round trip (host and client in a test room) with Bun:

bun -e '
const u = "wss://signal.example.com/TestRoom123", p = ["rech-signal-1"];
const h = new WebSocket(u, p), log = m => console.log(m.data);
h.onmessage = log;
h.onopen = () => { h.send(JSON.stringify({ type: "hello", role: "host", auth: "test" }));
  const c = new WebSocket(u, p); c.onmessage = log;
  c.onopen = () => { c.send(JSON.stringify({ type: "hello", role: "client", auth: "test" }));
    setTimeout(() => { c.send(JSON.stringify({ type: "answer", sdp: "hi" })); }, 200);

10. Protocol: rech-signal-1

This is all a compatible server has to do. Anything that implements it (Deno, Go, nginx + a script) works with rech.

HTTP

RequestResponse
GET /ping{"rech-signal":1}, which is how rech connect recognises a signal host
GET /<room> + Upgrade: websocket, subprotocol rech-signal-1101, echoing the subprotocol. <room> is 8–32 base58 characters.
anything elseOptional landing page. It must not need the #fragment server-side (it never arrives).

Frames (JSON text)

DirectionFrameServer does
any → server, first{type:"hello", role:"host"|"client", auth}The first host opens the room and fixes its auth. Later peers must match it. A client with no room gets close 4404.
server → peer{type:"welcome", peer, hostPresent}Host peer id is "host"; clients get a random id
server → host{type:"peer-join"|"peer-leave", peer}On client join and leave
server → clients{type:"host-leave"}When the host disconnects
client → host{type:"answer"|"candidate"|…}Forward to the host, adding from:<peer>
host → client{type:"offer"|"candidate"|…, to:<peer>}Forward to that client as is
any{"type":"ping"} (exact bytes)Reply {"type":"pong"}. On Cloudflare use setWebSocketAutoResponse so pings don't wake the object.

Close codes

CodeMeaning
1008expected hello or forbidden (auth mismatch). Never echo the auth.
1013room full (reference limit: 32 clients)
4404host offline: the client arrived and no host has the room open
1000replaced by a newer host connection (host restarted)

Room state lives only while someone is connected, so a restarted relay loses nothing that matters: hosts reconnect and reopen their rooms. Payloads are opaque. The server must forward SDP and candidates unchanged and never parse or log them.

11. Hardening checklist

  • TLS always for anything off-LAN (Caddy, Funnel, the platform, or Cloudflare).
  • Don't log frames. Access logs are fine, but SDPs contain candidate IPs.
  • Limits: clients per room (32), message size (64 KB), idle timeout (120 s; hosts ping every 20–60 s).
  • Rate limits per IP on upgrades. Caddy's rate_limit plugin or Cloudflare WAF rules, for a public relay.
  • Single process for the in-memory relay (or sticky routing). The Cloudflare version doesn't need this.
  • No TURN here. If you add TURN, give out short-lived credentials (1 h), since a TURN relay carries real bytes and costs real money.
  • Run unprivileged (the systemd unit and Dockerfile above do).
